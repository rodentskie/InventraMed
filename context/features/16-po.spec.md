### Purchase Orders Page

This will be on `apps/app`.
List, create, view-detail and receive page for purchase orders (POs). Per @context/features/10-purchase-orders.spec.md there is **no update or delete** on the API yet — a PO can only be created, listed, viewed and received in full. Uses the existing `NAV_ITEMS` entry and its two sublinks in `src/lib/nav.ts` (no change needed there):

```ts
{
  label: "Purchase Orders",
  href: "/purchase-orders",
  children: [
    { label: "Create", href: "/purchase-orders/new" },
    { label: "Receive", href: "/purchase-orders/receive" },
  ],
}
```

Because these sublinks are dedicated routes (not drawer triggers), Create and Receive are **full pages** here, unlike the drawer pattern on `medicines`/`suppliers`. Get one is also a full page (a PO's items + receipts don't fit a drawer well). List keeps the same table + pagination shape as the other pages.

## Requirements

### Routing & layout

- `GET /purchase-orders` → `/purchase-orders`, at `app/(app)/purchase-orders/page.tsx`
- `POST /purchase-orders` → `/purchase-orders/new`, at `app/(app)/purchase-orders/new/page.tsx`
- `GET /purchase-orders/{id}` → `/purchase-orders/[id]`, at `app/(app)/purchase-orders/[id]/page.tsx`
- `POST /purchase-orders/{id}/receive` → `/purchase-orders/receive`, at `app/(app)/purchase-orders/receive/page.tsx`
- All four live under the `(app)` route group, same as `medicines`/`inventory-entries`/`suppliers`, so they get the shared guard + side nav + top nav for free
- Widen the `proxy.ts` matcher from `[..., "/suppliers", "/suppliers/:path*"]` to also cover `/purchase-orders`, `/purchase-orders/:path*` (this one pattern covers `/new`, `/receive` and `/[id]` too)

### Supplier & medicine lookups (shared across these pages)

Like the inventory entries page's medicine lookup (@context/features/14-inventory-page.spec.md), `PurchaseOrder` only carries `supplier_id` and `PurchaseOrderItem` only carries `medicine_id` — neither is joined server-side. Two lookups are needed:

- **Supplier lookup**: fetch once per page load via `listSuppliers({ limit: 100, offset: 0 })` (the API's max page size) into a `Map<string, Supplier>` keyed by `id`. Used on the list and detail pages to render a supplier name instead of a raw id. Same known limitation as the medicine lookup: only covers the first 100 active suppliers and excludes deleted ones; a PO referencing a supplier outside that set falls back to showing the raw `supplier_id`
- **Medicine lookup**: same approach via `listMedicines({ limit: 100, offset: 0 })`, used on the detail page to resolve each item's (and each receipt item's, via its `purchase_order_item_id`) medicine name. Same fallback to the raw id
- The create page's item picker does **not** use these bulk lookups — it reuses the existing `MedicineCombobox` (type-to-search against the API), same reasoning as the inventory entries create drawer

### Get all (list page)

- Heading ("Purchase Orders") with a "New Purchase Order" button top-right that links to `/purchase-orders/new` (a `LinkButton`, not a drawer trigger)
- Table listing purchase orders: Supplier, Status, Order Date, Expected Date, Created At, Actions
  - Supplier resolved via the supplier lookup map, falling back to the raw `supplier_id`
  - Status rendered with the `Tag` snippet, one color per status: `gray` (`draft`), `blue` (`ordered`), `orange` (`partially_received`), `green` (`received`), `red` (`cancelled`); capitalized label (e.g. "Partially Received")
  - Expected Date shows an em dash or similar when `null`
  - Actions column has one icon button: View, linking to `/purchase-orders/{id}`. No Update/Delete — not supported by the API
- Empty state (no purchase orders yet) uses the `EmptyState` snippet
- Data source: `GET /purchase-orders` (query params: `limit`, `offset` only — the API has no filters for this endpoint)
- Responsive: table scrolls horizontally on narrow viewports instead of breaking layout

### Pagination

- Same pattern as the other pages: `PaginationRoot` + `PaginationPrevTrigger` / `PaginationNextTrigger`, no page-number list
- Fixed `limit` (e.g. 20); `offset` tracked in component state, incremented/decremented by `limit` per click
- `PurchaseOrderListResponse` returns `{ data, total, limit, offset }` — Next disabled when `offset + limit >= total`; Previous disabled when `offset <= 0`, same as the other list pages (don't rely on `data.length < limit`)

### Create (page, not drawer)

- `/purchase-orders/new`: Heading ("New Purchase Order"), a Cancel link back to `/purchase-orders`, and the form
- Fields:
  - Supplier (`Combobox`, required) — new `SupplierCombobox` component (`src/components/purchase-orders/SupplierCombobox.tsx`), mirroring `MedicineCombobox` (debounced ~300ms, calls `listSuppliers({ name, limit: 20, offset: 0 })` per keystroke, shows an initial page before typing)
  - Order Date (date, required)
  - Expected Date (date, optional) — client-side hint only that it should not be before Order Date; the authoritative check is the API's `400`
  - Notes (textarea, optional, maxLength 500)
  - Items (required, 1–100 rows): a dynamic list, each row with a Medicine (`Combobox`, required — reuse `MedicineCombobox` from `src/components/inventory-entries/MedicineCombobox.tsx`) and Quantity Ordered (number, required, min 1); an "Add Item" button appends an empty row, each row has a Remove button (disabled when it's the only row); client-side blocks adding/selecting the same medicine twice across rows (the API rejects a repeat with `items[i].medicine_id is repeated`, but the form catches the common case before submit)
- Submits `POST /purchase-orders` with `{ supplier_id, order_date, expected_date, notes, items: [{ medicine_id, quantity_ordered }] }`; omit/empty `expected_date` and `notes` per the API storing them as no value
- On success (`201`) redirect to `/purchase-orders/{data.id}` and toast success
- `400` (field or item validation — item messages are positional, e.g. `items[1].quantity_ordered must be greater than zero`) and `404` (`supplier not found` / `medicine not found`, e.g. a stale combobox selection deleted concurrently) both show the server's `error` message as a form-level alert (mirrors the inventory entries drawer's `Alert` usage) and keep the form filled in so the user can correct and resubmit
- Use the `Field` snippet for labels/validation messages and `Toaster` for the success toast

### Get one (detail page)

- `/purchase-orders/[id]`: Heading (e.g. "Purchase Order" + a short id fragment), a Back link to `/purchase-orders`
- Header section (via the `DataList` snippet or similar): Supplier (resolved via lookup, fallback to raw id), Status (`Tag`, same color mapping as the list), Order Date, Expected Date (em dash when `null`), Notes (em dash when `null`), Created At
- Items table: Medicine (resolved via the medicine lookup, fallback to raw `medicine_id`), Quantity Ordered
- Receipts section: empty state ("Not received yet") when `receipts` is `[]`; otherwise one block per receipt (there's at most one today, since only full-receive exists) showing Received At, Notes (em dash when `null`), and a nested table of that receipt's items — Medicine (resolved by looking up the item's `purchase_order_item_id` in the PO's own `items` array first, then the medicine lookup), Quantity Received, Quantity Damaged, Quantity Returned
- "Receive" button, shown only when `status` is `draft` or `ordered`, linking to `/purchase-orders/receive?id={id}`
- Loading/error states like the other pages; `404` (deleted or bad id) shows a not-found message with the Back link, instead of throwing
- Data source: `GET /purchase-orders/{id}`

### Receive (page)

- `/purchase-orders/receive`: Heading ("Receive Purchase Order")
- Without a `?id=` query param: reuses the same list table shape as the Get-all page (Supplier, Status, Order Date, Expected Date, Created At) plus a Receive action button per row, **enabled only** when that row's status is `draft` or `ordered` (disabled elsewhere — a purchase order that's already `received`/`cancelled`/`partially_received` can't be received again through this pass). Same `GET /purchase-orders` pagination as Get-all; no server-side status filter exists yet (see Open Questions in @context/features/10-purchase-orders.spec.md), so this page does not attempt to filter the list itself — it just disables the action per row
- With `?id=` present (e.g. arriving from the detail page's "Receive" button): skip straight to the confirm step for that PO — fetch it via `getPurchaseOrder(id)` and open the confirmation dialog immediately; an id that turns out not receivable (already received by someone else) shows the `409` error and leaves the user back on the plain list view
- Confirm dialog (`DialogRoot`, not the drawer): shows the PO's supplier and item count, an optional Notes field (textarea, maxLength 500, prefilled empty), and Confirm/Cancel buttons
- Confirms via `POST /purchase-orders/{id}/receive` with `{ notes }` (empty/omitted when blank); on success (`201`) close the dialog, toast success (e.g. "Purchase order received"), and refresh the underlying list
- `409` (status no longer `draft`/`ordered`) closes the dialog and toasts the server's `error` message instead of retrying
- `404` (PO deleted concurrently) closes the dialog, toasts an error, and refreshes the list
- `400` (e.g. `notes` too long) keeps the dialog open and shows the error inline, same as the other forms

### Data fetching

- Server Actions in `src/actions/purchase-orders.ts` returning `ActionResult<T>` (see `src/actions/suppliers.ts`), using `process.env.API_URL` / `API_PREFIX` and forwarding the `access_token` cookie as `Authorization: Bearer <token>`
  - `listPurchaseOrders({ limit, offset })` → `GET /purchase-orders`
  - `createPurchaseOrder(input)` → `POST /purchase-orders`
  - `getPurchaseOrder(id)` → `GET /purchase-orders/{id}`
  - `receivePurchaseOrder(id, input)` → `POST /purchase-orders/{id}/receive`
- Types in `src/types/purchase-order.ts` mirroring `PurchaseOrder`, `PurchaseOrderItem`, `PurchaseOrderReceipt`, `PurchaseOrderReceiptItem`, `PurchaseOrderDetail`, `PurchaseOrderListResponse`, `CreatePurchaseOrderRequest`/`CreatePurchaseOrderItem` (as `CreatePurchaseOrderInput`/item), `ReceivePurchaseOrderRequest` (as `ReceivePurchaseOrderInput`) from the swagger schemas
- Reuse `listSuppliers` from `src/actions/suppliers.ts` and `listMedicines` from `src/actions/medicines.ts` for both the bulk lookups and the comboboxes — no new list actions needed for those
- List/detail refresh after create/receive: re-run the relevant action and update local state (client components); no need for full page reload beyond the create → detail redirect

### Components

Under `src/components/purchase-orders/`:

- `PurchaseOrdersPageClient.tsx` — Get-all page: owns list state, pagination offset, supplier lookup map
- `PurchaseOrdersTable.tsx` — renders the list table + empty state + View action (shared shape reused by the Receive page's plain-list view, via a prop for the row action)
- `PurchaseOrderStatusTag.tsx` — small wrapper around the `Tag` snippet with the status → color/label mapping, shared by the list, detail and receive pages
- `SupplierCombobox.tsx` — type-to-search supplier picker for the create page (mirrors `MedicineCombobox`)
- `PurchaseOrderFormPage.tsx` (or inline in `app/(app)/purchase-orders/new/page.tsx`) — the create form, including the dynamic items list
- `PurchaseOrderDetail.tsx` — Get-one page body: header, items table, receipts section, conditional Receive link
- `ReceivePurchaseOrderPageClient.tsx` — Receive page: owns the plain-list view and the `?id=` deep-link flow
- `ReceivePurchaseOrderDialog.tsx` — the confirm dialog (notes field + confirm/cancel)
